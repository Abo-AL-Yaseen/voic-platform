# VOIC: قواعد المشروع وخطة العمل

## اعتماد إدارة المحتوى — 2026-11-25

بطلب صريح تنفذ هذه المرحلة إدارة المنتجات والتصنيفات والاستخدامات والوصفات والصفحات
المنظمة والوسائط للمدير ومحرر المحتوى، مع مسودات منفصلة ومراجعة ونشر صريح من المدير.
تفاصيل القرارات والمخطط والعقود والاستيراد والحفظ والاختبار اليدوي في
[دليل إدارة المحتوى](content-management.md). تستخدم البنية الحالية وMySQL المحلي فقط،
وتحفظ المنتجات الـ11 والهويات والأصول ولقطات الاستفسارات. لا تعني بيانات التطوير اعتماد
الإنتاج؛ تبقى كتابة الموظفين الإنتاجية معطلة حتى MFA. إدارة الموظفين والنشر خارج هذه المرحلة.
تصحيحات واجهة الاستفسارات ضمن الطلب، مع الحفاظ على الرحلة التي اختبرها المستخدم.

آخر تحديث: 2026-11-25. هذه الوثيقة هي المرجع المعتمد لقواعد المشروع وقراراته وخطوات العمل، وتُستخدم مباشرة مع Codex. [الحالة الحالية](current-state.md) تفصل المنفذ عن المطلوب، و[متطلبات الكتالوج](product-catalog.md) تفصل أول ميزة تكامل مقترحة.

## القرارات المعتمدة

- VOIC منصة تعريف بالمنتجات واختيارها والاستفسار عن التوريد لشركة مصانع الزيوت النباتية في نابلس. يستمر العمل في المستودع والتطبيق الحاليين، مع الواجهة والخلفية المستقبلية والوثائق في مشروع واحد.
- يستمر React وTypeScript والتصميم الكريمي/الزيتوني والشعار والصور الأصلية وخطوط Alexandria ورخصتها وسمات Git LFS. لا إعادة تصميم أو استبدال تطبيق أو ترحيل إطار دون طلب منفصل.
- الخلفية المعتمدة: NestJS مع TypeScript، وقاعدة MySQL بمحرك InnoDB، وTypeORM مع migrations فقط و`synchronize: false`. اعتُمدت بتاريخ 2026-11-23؛ Laravel وPostgreSQL في المراجع التاريخية ليسا خيارات المشروع الحالية. إعداد وتشغيل الأساس موثق في [دليل الخلفية](../backend/README.md).
- الإعداد المحلي المعتمد بتاريخ 2026-11-23 هو MySQL Server المثبت على Windows، وتتم إدارته ببرنامج MySQL Workbench المنفصل عن الخادم. الاتصال تحدده متغيرات البيئة، مع قاعدة ومستخدم منفصلين لـVOIC وInnoDB وutf8mb4. لا استخدام لـDocker ولا تعديل لحاويات أو وحدات تخزين في هذا الإعداد؛ تشغيل الخلفية وmigrations مستقل عنه.
- اللغات الحالية العربية افتراضيًا مع RTL، والإنجليزية مع LTR فقط. رمز لغة غير مدعوم في رابط قديم يعرض العربية دون فقد مسار الصفحة أو معاملات البحث الأخرى.
- أسماء العلامات تستخدم أسماءها العربية المعتمدة والتهجئات اللاتينية الرسمية الحالية في الإنجليزية، مثل الغزال / Al-Ghazal والنباتين / Al-Nabatin والكواكب / Al-Kawakib. لا ترجمة حرفية للعلامة ولا تغيير للمعرف أو slug.
- تبقى المسارات والمعرفات والـslugs وارتباطات الوصفات ووحدات التعبئة متوافقة. ترتيب المنتجات الأربعة في الرئيسية: `ghazal-butter` ثم `nabateen` ثم `kawakeb` ثم `ghazal`. المقارنة حتى ثلاثة منتجات؛ اختيار الاستفسار مستقل عنها.
- لا تُختلق مواصفات أو مكونات أو صور أو توفر أو شهادات أو موافقات تصدير. تعارض المصادر يحتاج مراجعة الشركة، ولا يُحل بالدمج. ملاحظات البحث والمصادر تبقى داخلية ولا تظهر في واجهة أو API عام.
- النصوص التجارية والقانونية/الخصوصية تحتاج اعتمادًا بشريًا؛ وجود مسودة في المصدر ليس إثبات اعتماد. لا أسعار عامة أو سلة شراء أو checkout أو دفع.

اعتمد صاحب المشروع تنفيذ الكتالوج العام للقراءة محليًا من البداية للنهاية على `mahmoud` بتاريخ 2026-11-23، مع حل القرارات التقنية الروتينية وتوثيقها. [دليل التنفيذ](catalog-implementation.md) يسجل المخطط والعقد وقرارات التوافق؛ هذا التفويض لا يشمل اعتماد محتوى الإنتاج أو الحسابات أو CRUD الموظفين أو إرسال الاستفسارات أو النشر التشغيلي.

اعتمد صاحب المشروع بتاريخ 2026-11-24 تنفيذ الحسابات والمصادقة الحقيقية للعملاء وربط الشاشات الحالية، بما في ذلك التسجيل المفتوح والجلسات وتأكيد البريد والاستعادة والملف الشخصي وأمان الحساب وصلاحيات الوصول الأساسية. [دليل المصادقة](authentication.md) يوثق العقود والقرارات والتحقق؛ لا يشمل هذا التفويض إرسال استفسارات التوريد أو CRUD الموظفين أو النشر أو إعداد موظفين افتراضيين.

## حدود المعمارية وإدارة البيانات

اعتمد صاحب المشروع بتاريخ 2026-11-24 تنفيذ استفسارات التوريد للعملاء من البداية للنهاية، مع إصلاح بطاقة رفض دخول الموظفين وعناوين الحساب. يشمل التفويض مسودات مملوكة للحساب، إرسالًا ذريًا مع منع التكرار، متابعة العميل وإشعارات محفوظة لإعادة المحاولة. [دليل الاستفسارات](customer-inquiries.md) يسجل القرارات والعقود والتحقق. كانت إدارة الموظفين للاستفسارات خارج تلك المرحلة؛ اعتُمدت لاحقًا في الطلب الموثق أدناه. النشر التشغيلي خارج النطاق، والحسابات والكتالوج محفوظان.

1. **Services**: طلبات HTTP والأنواع وعقود البيانات فقط؛ لا عرض أو hooks داخل الخدمات.
2. **Utils عند الحاجة**: تحويل أو تطبيع أو تنسيق فعلي؛ لا تُنشأ طبقة زائدة لمجرد مطابقة أسماء مجلدات.
3. **Feature-Based TanStack React Query Hooks**: ملكية حالة الخادم والتخزين المؤقت لكل ميزة، بمفاتيح مركزية في `hooks/<feature>/keys.ts` وعمليات `queries/` و`mutations/` حسب العقود الحقيقية المطلوبة.
4. **Pages**: العرض والنماذج وحالة الواجهة المحلية، وتستهلك hooks الميزة لعمليات الخادم.

- يبقى QueryClient مستقرًا واحدًا. تعكس مفاتيح القراءة اللغة والبحث وكل الفلاتر والفرز والتقسيم ونطاق المستخدم الفعلي.
- لا تتشارك البيانات العامة والمقيدة مدخلات قد تعبر حدود الصلاحيات. الاستعلامات الخاصة تحمل `meta.private = true` ونطاق المستخدم، وتُلغى وتُزال عند تسجيل الخروج أو تبديل الحساب، مع منع وصول استجابات متأخرة لحساب سابق.
- تُحفظ أشكال الاستجابة وعضوية القوائم وترتيبها الفعلي عند تحديث التخزين المؤقت. يُستخدم تحديث آمن أو إبطال موجّه؛ لا إبطال شامل ولا تخمين محتوى/أعداد قوائم مفلترة أو مقسمة.
- لا تُحفظ بيانات اعتماد أو ذاكرة خاصة في `localStorage`، ولا أسرار خادم في إعدادات المتصفح. لا إعادة محاولة تلقائية لعملية كتابة غير آمنة دون ضمان منع التكرار من الخادم.
- تُراجع الشيفرة الحالية والعقد الحقيقي أو المعتمد قبل التكامل، ميزة واحدة كل مرة. الخدمة العامة ومزود QueryClient وملفات المفاتيح الحالية بنية جاهزة وليست إثبات تكامل.
- بعد الربط الحقيقي، يظهر فشل API كخطأ مناسب قابل لإعادة المحاولة؛ يُمنع fallback صامت إلى البيانات المحلية. نسخة سابقة ناجحة لنفس السياق يمكن عرضها مع توضيح فشل تحديثها وفق متطلبات الميزة.

## متطلبات الحسابات والاستفسارات والموظفين المحفوظة

متطلبات الحسابات الأساسية أدناه منفذة ضمن المهمة المعتمدة بتاريخ 2026-11-24؛ حفظ الاستفسارات وإرسالها ومتابعتها من حساب العميل ضمن المهمة الحالية المعتمدة. عمليات الموظفين للاستفسارات ضمن الطلب الحالي؛ تبقى MFA وإدارة الموظفين العامة مستقبلية. تحدد أدلة المصادقة والاستفسارات ومساحة المبيعات النطاق الفعلي وحدوده.

- التصفح العام متاح دون حساب. يستطيع الأفراد والشركات التسجيل دون موافقة موظف، ويجب تأكيد البريد قبل إرسال استفسار توريد.
- مدخل تسجيل الدخول واحد للعملاء والموظفين. العميل يصل إلى حسابه واستفساراته فقط. استعادة كلمة المرور لا تكشف وجود حساب.
- صلاحيات الموظفين يوفرها الخادم للأدوار `administrator` و`sales` و`content_editor`؛ لا يُمنح دور موظف أو مدير عبر التسجيل العام. تتحقق كل عملية محمية من التفويض والملكية على الخادم؛ إخفاء الروابط أو حارس الواجهة ليس تفويضًا.
- المسار المطلوب: اختيار المنتجات ← تسجيل الدخول وتأكيد البريد ← تأكيد العبوات والكميات والوجهة ← المراجعة ← الإرسال ← المتابعة. الاستفسار طلب تراجعه الشركة وليس بيعًا مقبولًا تلقائيًا.
- يجب التحقق من ارتباط المنتج بالعبوة وصحة الكميات الإيجابية، وفصل الرسائل المرئية للعميل عن ملاحظات الموظفين الداخلية.
- حفظ الاستفسار عملية مترابطة لا تتجزأ، مع منع تكراره على الخادم عند إعادة المحاولة. فشل الإشعار لا يفقد الطلب المحفوظ ولا ينشئ طلبًا آخر.
- تتطلب التكاملات الحقيقية جلسات آمنة، وحماية CSRF حيث تنطبق، والتحقق من المدخلات وحدود الطلبات، والتحقق متعدد العوامل للموظفين. يلزم توثيق سجل تدقيق لا يمكن للعميل تعديله وصلاحية الوصول إليه.
- تظل واجهات preview وتجاوزات الموظفين محصورة بالتطوير ومستبعدة من الإنتاج. نموذج البريد/النسخ الحالي لا يثبت تسليم رسالة أو حفظ طلب أو متابعته.

لا تفوض هذه الخطة تلقائيًا بناء خلفية أو migrations أو نشرًا أو تنفيذ جميع المراحل. كل مهمة تحدد نطاقها، وتُسجل القرارات قبل العمل التابع لها.

## طريقة العمل والتحقق

- افحص `AGENTS.md` و`frontend/AGENTS.md` والحالة الحالية والملفات المعنية أولًا. احفظ العمل غير المتعلق بالمهمة، ولا تستبدل التطبيق أو الأصول لتجاوز مشكلة.
- فرع العمل الدائم الوحيد هو `mahmoud`؛ لا تُنشأ فروع ميزات أو مهام جديدة. تُحفظ التغييرات غير الملتزم بها وكل الالتزامات الفريدة قبل التجميع. يُتحقق من وجودها على `origin/mahmoud` قبل حذف أي فرع آخر محلي أو بعيد، دون force-push أو إعادة كتابة التاريخ. يُضبط كفرع GitHub الافتراضي إن سمحت الصلاحيات؛ وإلا يبقى الافتراضي القديم مؤقتًا مع توضيح الإعداد المطلوب.
- لا تشغيل أو إيقاف أو إعادة تشغيل أو تعديل لحاويات أو قواعد أو وحدات تخزين أي مشروع آخر، ولا حذف لوحدات تخزين قواعد البيانات. يُستخدم خادم MySQL المحلي بقاعدة ومستخدم منفصلين لـVOIC فقط؛ لا يُشغّل Docker Desktop. تُدخل كلمة مرور مسؤول MySQL محليًا عند الحاجة، دون إرسالها في المحادثة أو إعادة تعيين كلمة مرور موجودة.
- عرّف نتيجة المستخدم ومعايير قبول وحالات فشل وحدود بيانات وتوافق قبل التكامل. أي عمل قاعدة بيانات يحتاج معيار استعادة وتراجع؛ التفاصيل المستقبلية في FR-025 بمتطلبات الكتالوج.
- حافظ على اتساق هذه الوثيقة ومتطلبات الميزة مع القرارات الفعلية. تعديل قاعدة معتمدة يحتاج طلبًا صريحًا يوضح الأثر والتوافق والاستعادة؛ لا تتحول مقترحات مرجع تاريخي إلى قرارات ضمنية.
- من `frontend/` شغّل `pnpm.cmd test` و`pnpm.cmd typecheck` و`pnpm.cmd build` للتغييرات التطبيقية، وسجل ما اختُبر فعلًا وحدوده. لا تثبيت أو ترقية مكتبات دون حاجة منفصلة.
- قبل الالتزام راجع الملفات المرحلية للأسرار والحذف غير المقصود وتغييرات الأصول. لا تلتزم ببيئات خاصة أو جلسات أو مخرجات تشغيل. يكون الالتزام والدفع إلى `mahmoud` وفق السياسة أعلاه.

## مرجعية الوثائق والمراجعات

- هذه الوثيقة تحفظ قواعد المشروع المعتمدة سابقًا وتستبدل تعليمات تدفق العمل الخاصة بالأداة السابقة؛ نطاق اللغات عدله صاحب المشروع إلى لغتين بتاريخ 2026-11-23. الاعتماد الأول للقواعد كان في التاريخ نفسه.
- متطلبات الكتالوج حُفظت من المسودة غير الملتزم بها مع قصصها الست و25 متطلبًا و29 سيناريو قبول وثمانية مقاييس، بعد تحديث اللغة والمراجع. لا توجد إجابة معتمدة لسؤال نقص الترجمة السابق.
- مراجعة جودة المسودة السابقة كانت 16/16 مع استثناء قيود التقنية التي طلبها المستخدم صراحةً؛ هذه مراجعة وثائق وليست دليل تنفيذ أو اعتماد محتوى. تظل الأسئلة المفتوحة والافتراضات في متطلبات الكتالوج ظاهرة للمراجعة.
- [ملاحظات المنتجات](../frontend/docs/product-data-notes.md) للمصادر والحقول المتعارضة داخليًا، و[حدود التكامل](../frontend/docs/frontend-integration-boundaries.md) للعقود المفقودة في الواجهة.
- [الخطة التاريخية](reference/VOIC_Production_Plan_AR.md) محفوظة دون تغيير بصفتها مقترحًا قديمًا؛ لا تتقدم على القواعد الحالية، ولا تعتمد تقنيتها أو مخططها أو endpoints أو أرقام سعتها.

## اعتماد مساحة المبيعات والاستفسارات — 2026-11-24

طُلب تنفيذ متابعة الموظفين للاستفسارات بعد الميزة المكتملة في `2d89755`، مع القوائم
والإحصاءات الفعلية والمحادثة والملاحظات الداخلية وتدقيق الإجراءات. المعتمد مفصل في
[دليل مساحة المبيعات](staff-inquiries.md)، بما فيه الحالات الموحدة، التحقق على الخادم،
وحفظ النص عند التعارض. لا إعادة فتح للاستفسار المغلق في هذه المرحلة. إنشاء حساب الموظف
أو ترقية حساب قائم يتم محليًا بأداة تفاعلية وتأكيد صريح دون تغيير كلمة مرور الحساب القائم.
تُسمح إجراءات الموظفين محليًا بإعداد تطوير صريح وبريد ملتقط فقط؛ تبقى معطلة في الإنتاج
إلى حين تنفيذ MFA. إدارة الموظفين والمحتوى والنشر والدفع خارج هذا الطلب.

## اعتماد إدارة الموظفين وأمانهم — 2026-11-25

طلب المستخدم صراحةً استكمال إدارة الموظفين والدعوات والأدوار والإيقاف وإلغاء الجلسات،
وفرض MFA على المسؤول والمبيعات ومحرر المحتوى، وتوصيل سجل التدقيق الفعلي.
المصفوفة الموحدة والتشفير والاسترداد والصلاحيات وإجراءات المشغّل موثقة في
[دليل أمان الموظفين](staff-security.md). تُحفظ الحسابات وكلمات المرور والتسجيلات القائمة؛
التسجيل الأول للعامل يجريه صاحب الحساب بنفسه بعد إعادة التشغيل. إعداد الكتابة المحلي لا
يتجاوز MFA، وتظل العمليات التجارية في الإنتاج معطلة حتى اعتماد تشغيلي صريح.
ترحيل إضافي واحد دون إعادة ضبط التطوير؛ الاختبارات المدمرة على قاعدة MySQL مؤقتة فقط.
لا نشر أو بريد خارجي أو إنشاء افتراضي لموظفين، ولا تغيير في البيانات المنشورة.
