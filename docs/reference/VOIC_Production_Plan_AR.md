# خطة تحويل VOIC إلى موقع إنتاجي

تاريخ المراجعة: 22 نوفمبر 2026. الحالة: خطة تنفيذ أولية؛ لا يوجد نشر أو باك إند منفذ بهذه الوثيقة. تحديث معتمد: اعتماد معمارية React Query وفق نمط FitMind؛ التعديل توثيقي ولا يعني تثبيت المكتبات أو ربط التطبيق بعد.

## 1. الهدف وحدود المرحلة

نحافظ على React والهوية المعتمدة، ونضيف API وقاعدة بيانات ولوحة إدارة وحسابات عملاء وطلبات توريد محفوظة. التصفح والوصفات والمقارنة والاختيار تبقى عامة. تسجيل الدخول وتأكيد البريد مطلوبان عند إرسال طلب توريد ومتابعته. التواصل العام يمكن أن يبقى متاحًا دون حساب مع ضوابط منع الإساءة. لا أسعار عامة ولا دفع إلكتروني ولا التزام بيع تلقائي.

افتراض العمل: الطلب طلب توريد/RFQ تراجعه الشركة وتؤكد تفاصيله لاحقًا. لو المطلوب طلب شراء ملزم يتغير نموذج العمل والحالات والموافقات. لا نضيف مخزونًا أو شحنًا أو فواتير دون احتياج معتمد.

## 2. ما فُحص فعلًا

- المسار المحلي voic-project يحوي React وTypeScript وVite وTailwind، مع scripts للبناء وفحص الأنواع واختبار الكتالوج.
- النسخة المحلية أقدم من تقرير Make version 5: لا تحتوي Pages.tsx أو InquiryForm.tsx أو recipes.ts أو i18n.ts الموصوفة بالتقرير. لا يجوز معاملتها كنسخة الإنتاج النهائية أو الكتابة فوق نسخة فيجما.
- يتوفر بنكا المنتجات والوصفات السابقان وخرائط الأصول في output/VOIC-Figma-Master.
- المصادر المتاحة: الموقع الرسمي، صفحة QR، الكتالوج الإنجليزي 8 صفحات، كتالوج 2025 من 10 صفحات، وملف Company Profile 2026 من 16 صفحة PDF فعلية. ترقيم الصفحات المطبوع داخل الملف الأخير غير متسق؛ الإحالات أدناه لترتيب PDF الفعلي.
- روجع نص ملف 2026 وصور صفحات المنتجات 8 إلى 15 المختارة. لا تدعي هذه المراجعة اعتماد الشركة للبيانات أو صحة شهادات حالية.
- لم تُنفذ اختبارات تطبيق أو أمن أو حمل في هذه المرحلة؛ الإجراء الحالي فحص مصادر وتصميم خطة.

## 3A. معمارية الفرونت المعتمدة رسميًا — نمط FitMind

هذا قرار معتمد من الفريق للفرونت، مستقل عن اختيار لغة الباك إند. Laravel ما زال اقتراحًا؛ React Query ليست مشروطة به. نعتمد React + TypeScript، وServices + Utils عند الحاجة + Feature-Based Hooks + Query Keys + Smart Cache Management + Clean Pages. ملفات المكونات والصفحات .tsx، وملفات الخدمات والأنواع والأدوات والـHooks التي لا تحتوي JSX يمكن أن تبقى .ts.

### فصل المسؤوليات

| الطبقة | المسؤولية | حدودها |
|---|---|---|
| services/ | HTTP requests وDTOs وPayload types حسب التنظيم | لا useQuery ولا useMutation ولا React UI |
| utils/ | Normalization وMapping وFormatters وPayload Builders عند الحاجة | لا مجلدات ودوال شكلية أو تغيير صامت للوحدات |
| hooks/<feature>/ | keys.ts وQuery Hooks وMutation Hooks وإدارة الكاش | تستدعي Services وتستخدم Utils عند الحاجة |
| pages/ | عرض البيانات وحالات التحميل والخطأ والتفاعل والفورمز | تستدعي Hooks؛ لا requests مباشرة ولا إدارة كاش |
| components/ | مكونات عرض مشتركة وواجهات صغيرة | لا تعيد بناء طبقة API موازية |

مسار الاستخدام: Page → Hook → Service → HTTP API. Utils أدوات مساعدة تُستدعى في الموضع المناسب وليست مرحلة إجبارية لكل request. تحويل DTO إلى نموذج مشترك للواجهة يكون واضحًا ومكتوب الأنواع؛ نستخدم select داخل Hook فقط إذا كان تحويل العرض الخاص بالمستهلك يستدعي ذلك، مع فهم شكل البيانات المخزن فعليًا في الكاش.

### تنظيم الملفات


الشجرة هدف تنظيمي تدريجي، لا ادعاء أن هذه الملفات أو endpoints موجودة الآن. لا ننشئ Hook أو Mutation folder لعملية غير موجودة. نحافظ على Services سليمة موجودة، وننقل الملفات بحذر مع تحديث imports وبقاء routes والـIDs. يمكن فصل أسماء خدمات public/admin أو جمعها حسب الحاجة، لكن query keys وresponse types يجب أن يميزاهما.

### QueryClient وHTTP Client

- QueryClient واحد مستقر لكل دورة تطبيق المتصفح، يلف التطبيق بـQueryClientProvider عند main.tsx؛ لا QueryClient جديد لكل صفحة أو render.
- نفحص package.json وlockfile في أحدث نسخة أولًا، ونستخدم package manager الموجود لتثبيت @tanstack/react-query وHTTP client إذا كانا ناقصين، دون خلط lockfiles أو ترقية عشوائية.
- services/api.ts يضبط baseURL وheaders وtimeouts وcredentials أو Bearer حسب المصادقة الفعلية، ويعيد أخطاء typed قابلة للعرض. لا نخزن أسرارًا في Vite env العامة.
- نمرر AbortSignal من queryFn عبر Service إلى HTTP client كي تعمل cancellations، ونفصل إلغاء الطلب عن خطأ يُعرض للزائر.
- staleTime وretry وrefetchOnWindowFocus تُحدد لكل طبيعة بيانات بعد قياسها: المحتوى العام أقل تغيرًا من حالات طلبات العميل. لا ننسخ أرقام FitMind بلا دراسة، ولا نعيد 401/403 أو أخطاء validation مرارًا. retry للكتابات لا يُفعّل عشوائيًا؛ طلبات التوريد تحتاج idempotency خادميًا.
- إعدادات واضحة لحالات pending/error/empty/refetching والـmutation pending. تعطيل الزر أثناء الإرسال feedback فقط، وليس بديلًا عن منع التكرار بالسيرفر.

### Query Keys حسب الميزة

- لكل Feature ملف keys.ts بدل تكرار strings داخل Hooks.
- المفاتيح تشمل كل ما يغيّر استجابة API: locale، البحث المرسل للسيرفر، الفلاتر، الفرز، page/pageSize أو cursor، ومعرف المنتج أو slug حسب العقد الحقيقي.
- قوائم public المنشورة تختلف عن admin drafts حتى لا تتداخل صلاحيات أو أشكال بيانات. تفصيل برقم أو slug يُختار بعقد موحّد؛ لا نفترض أن IDs الحالية أرقام.
- بيانات المستخدم الخاصة تُقسم حسب userId ومعرف الشركة عند وجود دعم شركات متعدد؛ لا تدخل التوكنات أو البيانات الحساسة في query keys.
- توحيد ترتيب الفلاتر التي لا يهم ترتيبها قبل بناء المفتاح، وإزالة القيم الفارغة بصورة ثابتة تمنع كاشًا مكررًا لنفس الطلب.
- عندما ينقص ID أو prerequisite نستخدم enabled أو آلية تعطيل مناسبة للإصدار المعتمد، ولا نرسل undefined إلى endpoint.

### Queries وMutations

قراءة Server Data عبر useQuery أو أداة Query مناسبة عند الحاجة، ضمن Hooks الميزة. لا useEffect + useState لنسخ نفس fetch/loading/error بلا سبب واضح. الـServices لا تعرف React Query. الـPages لا تنفذ POST/PATCH/DELETE مباشرة؛ تستخدم mutate أو mutateAsync من Hook وتعرض validation errors ونتيجة العملية. تسمية useProductById أو useProductBySlug تتبع endpoint الحقيقي، ولا نضيف endpoint لتوافق مثالًا فقط.

### سياسة الكاش الذكي

| السيناريو | السياسة |
|---|---|
| تحديث detail ببيانات كاملة من السيرفر | setQueryData بمفتاح detail الصحيح، ثم معالجة القوائم المتأثرة بشكل محدد |
| تعديل/حذف عنصر في قائمة بسيطة غير مقسمة وواضحة العضوية | تحديث immutable يحفظ Data Shape، إذا أمكن الحفاظ على الفرز والعدد بدقة |
| إنشاء عنصر يعيد السيرفر بياناته كاملة | تخزين detail؛ إدراجه بالقائمة فقط إذا كانت العضوية والترتيب والعدد معروفة؛ اكتمال الرد وحده لا يكفي |
| قوائم paginated أو فلاتر معقدة أو تغيير يجعل العنصر ينتقل بين القوائم | invalidateQueries للقوائم المتأثرة بدل تخمين الصفحة أو الإجمالي |
| إحصائيات وإجماليات وعلاقات متعددة | invalidation موجه للمفاتيح المتأثرة فقط |
| حذف/أرشفة منتج | التعامل مع detail والقوائم والاختيار والمقارنة دون إبقاء صفحة تعرض سجلًا محذوفًا؛ لا حذف تاريخ الطلبات |

التحديث بعد نجاح السيرفر ليس Optimistic Update. نبدأ به عندما يكون واضحًا؛ optimistic updates اختيارية وتحتاج cancel للقراءات المتعارضة وsnapshot وrollback عند الفشل ثم reconciliation. لا invalidate لكل التطبيق بعد كل mutation، ولا setQueryData عشوائي لكل filter. لا نضع كائنًا مبسطًا مكان رد pagination أو نمط مختلف. ننتظر invalidation عند اعتماد اكتمال UI عليه، ولا نُخفي فشل عملية الكتابة بإظهار نجاح محلي.

### Local UI State والمصادقة

- useState/Reducer للفورمز والمسودات وفتح dialogs والتبويبات والاختيار والمقارنة والبحث المؤقت. عند الحاجة للمشاركة وback navigation تكون الفلاتر في URL؛ الفلاتر المرسلة للـAPI تدخل queryKey أيضًا.
- لا ننسخ Server Data إلى local state إلا لمسودة تعديل مقصودة مع سياسة واضحة إذا وصل refetch أثناء الكتابة.
- نحدّث بيانات الجلسة عبر Hook مناسب؛ المصادقة الفعلية مسؤولية الباك إند. لا تحول React Query المستخدم إلى admin بمجرد قيمة مخزنة.
- logout/تبديل الحساب: إيقاف عرض المساحة الخاصة، منع بدء requests محمية جديدة، إلغاء queries الجارية الخاصة، إزالة الكاش الخاص بالمستخدم السابق، وتصفير بيانات الجلسة والمسودات الحساسة ذات الصلة. انتظار/تسوية عمليات الكتابة الجارية وفق سياسة واضحة؛ إلغاء query لا يلغي mutation محفوظة في السيرفر. تغيير الهوية يضمن ألا تظهر نتيجة متأخرة للحساب السابق.
- لا persistence لكاش خاص أو رموز دخول في localStorage افتراضيًا. يمكن إبقاء الكاش العام الآمن عند logout. لا نخلط كاش المتصفح بـCDN cache؛ بيانات الحساب لا تدخل shared CDN cache.

### تسلسل العمل الإلزامي لكل Feature

1. مراجعة أحدث ملفات الميزة ومكوناتها وServices الموجودة.
2. مراجعة endpoint وresponse/pagination والأخطاء والصلاحيات الحقيقية أو عقد API المعتمد أثناء بنائه.
3. إنشاء/تعديل Service وDTO/payload types، ثم Utils فقط إن لزمت.
4. keys.ts وQuery Hooks، وMutation Hooks للعمليات المتاحة فقط.
5. ربط الصفحة دون تغيير التصميم أو Navigation أو Business Logic.
6. إزالة manual fetch القديم بعد نجاح الربط؛ لا mock data ولا fallback صامت للبيانات المحلية لإخفاء فشل API في الميزة المرتبطة.
7. تطبيق سياسة كاش محددة للعملية وتبعياتها.
8. اختبار loading/error/empty/CRUD والصلاحيات والفلاتر وتبديل اللغة والحساب والـcache shape قبل الانتقال للميزة التالية.

ترتيب VOIC المقترح: products + categories + uses للقراءة العامة → تفاصيل المنتجات والاختيار والمقارنة → pages/site-settings → recipes → auth/account → inquiries → ميزات الإدارة React إذا كانت موجودة فعلًا. لو لوحة الإدارة server-rendered بحزمة Laravel، لا نفرض React Query داخلها؛ نطبقه على واجهات React المعنية، ونحافظ على صلاحيات الباك إند نفسها.

## 4. المعمارية والاستضافة

نفضل عنوانًا عامًا واحدًا: الواجهة من / وواجهة API من /api، ولوحة الإدارة من /admin؛ البوابة توجهها للخدمات المناسبة. هذا توصيف معماري، وليس افتراض ملكية دومين الشركة الحالي. لا ننقل DNS أو نبدل الموقع الرسمي دون تفويض المالك.

الزائر يصل عبر HTTPS وحافة CDN/WAF، ثم الأصول الثابتة أو API حسب الطلب. API وحده يتصل بقاعدة بيانات خاصة وتخزين الملفات. Queue worker يتعامل مع الإشعارات بعد حفظ العمليات. الصور العامة يمكن تخزينها مؤقتًا، أما بيانات العملاء والجلسات وطلبات التوريد فممنوع وضعها في shared CDN cache.

موقع الاستضافة المبدئي منطقة أوروبية قريبة من ألمانيا، ويُختبر زمن الوصول من فلسطين وألمانيا قبل الاختيار النهائي. الاستضافة الأوروبية لا تساوي وحدها امتثالًا قانونيًا. اختيار المورد والسعة والتكلفة يحتاج ميزانية شهرية وحجم استخدام تقريبي واحتياجات الاعتمادية. لا نعطي وعد عدد مستخدمين من دون اختبار محدد.

نبدأ بتطبيق واحد منظم وخدمات مدارة حيث تسمح الميزانية. إذا كانت الإتاحة أثناء تعطل خادم شرطًا، نستخدم نسختي API على الأقل وخدمات بيانات عالية الإتاحة؛ خادم واحد يبقى نقطة فشل مهما كانت ذاكرته. لا حاجة الآن إلى microservices أو Kubernetes.

## 5. الصلاحيات والحسابات

| الدور | المسموح | الممنوع |
|---|---|---|
| زائر | المحتوى المنشور والبحث والمقارنة والاختيار | إرسال طلب توريد أو الوصول لطلبات العملاء |
| عميل مؤكد البريد | ملفه، شركته، طلباته ومراسلاته المسموح بها | بيانات عميل آخر أو أدوات الإدارة |
| محرر محتوى | تعديل المنتجات والوصفات والصفحات وفق الصلاحية | إدارة المستخدمين أو رؤية الاستفسارات تلقائيًا |
| موظف مبيعات | معالجة الطلبات المصرح بها والرد وتحديث حالاتها | تعديل الأدوار أو أسرار النظام |
| مدير | المحتوى والطلبات وإدارة حسابات الموظفين ضمن صلاحياته | تجاوز سجل التدقيق أو الاطلاع على كلمات المرور |

حسابات الإدارة بدعوات أو إنشاء آمن فقط، ولا يوجد تسجيل عام لدور admin. يحدد السيرفر الدور ولا يقبله من نموذج العميل. MFA إلزامي للإدارة مع recovery codes ومراجعة عمليات الاسترداد. كل عملية محمية تُفحص في السيرفر؛ إخفاء زر في React ليس حماية.

## 6. رحلة طلب التوريد

1. الزائر يختار منتجًا وعبوة معروفة، أو يطلب التواصل حول حجم آخر دون اختراع variant.
2. يمكن تجميع مسودة احتياج متعددة المنتجات دون تحويلها إلى سلة شراء أو عرض سعر.
3. عند الإرسال يُطلب الدخول أو إنشاء الحساب وتأكيد البريد؛ تحفظ المسودة وتعود للمستخدم بعد الدخول. لا نحفظ بيانات حساسة أو جلسات في localStorage.
4. العميل يحدد الشركة ودولة الوجهة والكمية ووحدتها وملاحظاته. الهاتف اختياري إلا إذا أقر الفريق حاجة تشغيلية واضحة له.
5. السيرفر يتحقق من المنتجات المنشورة والعبوات والوحدات والكميات وطول النصوص، ثم يحفظ الطلب وبنوده وسجل البداية في transaction واحدة.
6. يستخدم مفتاح idempotency مع قيد قاعدة بيانات لمنع تكرار الإرسال عند النقر مرتين أو إعادة المحاولة.
7. بعد commit يُنشأ إشعار موثوق عبر outbox/queue. تعطل البريد لا يلغي الطلب المحفوظ ولا يسبب إدخالًا ثانيًا. الرسالة تؤكد الاستلام فقط.
8. يرى العميل رقم الطلب وحالته؛ يرى فريق المبيعات الطلب بلوحته. تميّز الملاحظات الداخلية عن الرسائل التي يراها العميل.

الحالات المبدئية: submitted، under_review، awaiting_customer، responded، closed، cancelled. نحدد انتقالات الحالات وحق كل دور، مع تاريخ تغييرات. responded لا تعني موافقة توريد أو عقدًا. لا نعرض accepted/paid/shipped دون تنفيذ عمليتها فعلًا.

## 7. قاعدة البيانات المقترحة

الحقول المشتركة تشمل id وcreated_at وupdated_at عند الحاجة، مع مفاتيح أجنبية وقيود uniqueness وفهارس. هذا تصميم أولي قبل ERD والمigrations النهائية.

| المجموعة | الجداول | أهم البيانات والقيود |
|---|---|---|
| الحسابات | users، roles، role_user، sessions، password_reset_tokens | email فريد، password_hash، verified_at، حالة الحساب، أدوار خادمية |
| العملاء | customer_profiles | user_id فريد، اسم الشركة، دولة ISO، هاتف اختياري؛ نسخة أولى شركة واحدة للحساب |
| التصنيف | brands، categories، uses + translation tables | مفاتيح ثابتة وأسماء محلية، لا تكرار السمن وزيت نفس الاسم كسجل واحد |
| المنتجات | products، product_translations | legacy_id فريد، slug ثابت، حالة draft/published/archived، ترتيب، featured_rank |
| العبوات | product_variants | product_id، قيمة عشرية، وحدة معيارية g/kg/ml/L، نوع تعبئة اختياري، حالة نشر؛ لا تحويل كثافة L إلى kg |
| العلاقات | product_use، product_category | مفاتيح مركبة تمنع الازدواج، توصيات الاختيار من الاستخدامات الفعلية |
| الأصول | media_assets، product_media | object_key، MIME، الحجم، الأبعاد، checksum، alt محلي؛ ملفات الصور خارج DB |
| الصفحات | pages، page_translations، page_sections | نصوص ومقاطع منظمة بمخطط محدد؛ لا JavaScript أو HTML عشوائي من المحرر |
| الوصفات | recipes، recipe_translations، recipe_ingredients، recipe_steps، recipe_product | ترتيب ومقادير ووحدات ومعرفات ربط المنتجات، دون ملء قيم مجهولة |
| الاتصال | site_settings، navigation_items | عنوان وبريد وروابط عامة معتمدة فقط؛ الأسرار في secret manager وليس إعدادات عامة |
| التوريد | inquiries، inquiry_items، inquiry_status_events، inquiry_messages | ملكية العميل، مرجع الطلب، دولة الوجهة، quantity+unit، snapshots لأسماء المنتجات والعبوات وقت الطلب |
| التواصل العام | contact_messages | وصول الموظفين فقط، منع الإساءة، سياسة احتفاظ مستقلة |
| التدقيق | audit_logs | الفاعل والعملية والهدف والتوقيت؛ قبل/بعد محدود لا يشمل كلمات المرور أو التوكنات |
| المصادر | content_sources، content_source_links، content_revisions | الملف/الصفحة وتاريخ المراجعة والتضارب واعتماد النشر؛ لا تخرج في public API |
| التشغيل | jobs، failed_jobs، notification_outbox | إعادة محاولة ومعالجة آمنة دون تكرار الإشعارات |

إلغاء نشر المنتج لا يمسح طلبات قديمة؛ نحفظ snapshot للبنود ونمنع حذفًا متسلسلًا للطلبات. حذف/إخفاء بيانات العميل يحتاج سياسة احتفاظ واضحة، وليس حذف كل السجل المالي أو التجاري تلقائيًا. فهرسة owner_id/status/date، slug وlegacy_id، ومفاتيح relations؛ pagination وحد أقصى لحجم الصفحة.

بيانات الصفحات من DB مع كاش وبطلان كاش عند النشر. التصميم والـcomponents وتوكنات الألوان ومسارات التطبيق تبقى في الكود، وليست محتوى قابلًا لتغيير عشوائي من الإدارة. ترجمة ar/en من البداية؛ de قابلة للإضافة إذا اعتُمد محتوى ألماني، لا مجرد زر لغة وهمي.

## 8. API والعقود

- Public: GET /api/v1/products، /products/{slug}، /categories، /uses، /recipes، /recipes/{slug}، /pages/{slug}، /site-settings. يعيد published فقط وDTOs بقائمة حقول مسموحة.
- Auth: تسجيل، دخول، خروج، تأكيد بريد، استعادة كلمة مرور، عرض جلسة المستخدم. مسارات session/CSRF حسب إعداد Sanctum الفعلي، لا نفترض أسماء قبل تثبيته.
- Customer: GET/PATCH /api/v1/me، POST/GET /api/v1/inquiries، GET /inquiries/{id}، إضافة رسالة أو طلب إلغاء حسب الحالة. ownership إلزامي على كل endpoint.
- Admin: CRUD للمحتوى والأصول، preview/draft/publish، إدارة الطلبات والحالات والأدوار وفق policies منفصلة.
- Contact: POST /api/v1/contact مع rate limits والتحقق من المدخلات.
- استجابات موحدة وvalidation errors مناسبة للغتين، واستعمال 401/403/404/422/429/5xx دون كشف وجود طلب خاص أو تفاصيل تشغيلية.
- فرز وفلاتر بقائمة مسموحة وpagination؛ لا نمرر أسماء أعمدة SQL من المستخدم.
- OpenAPI عقد موثق مع أمثلة، واختبارات تطابق React مع شكل الرد؛ نُبقي الروابط القديمة وproduct IDs عاملة.

## 10. خطة الأمان

- HTTPS، secure/HttpOnly session cookie بإعداد SameSite مناسب، CSRF للعمليات التي تستخدم cookies، وضبط CORS للأصول المعتمدة فقط عند الحاجة. Same-site topology أفضل لتبسيط الإعداد.
- استعمال مكتبات framework للمصادقة وhashing بدل تشفير يدوي، session rotation عند الدخول وتغيير الصلاحيات، وإلغاء الجلسات عند reset أو تعطيل الحساب.
- rate limits مستقلة للتسجيل والدخول والاستعادة والطلبات والرسائل، حسب الحساب وIP مع مراعاة الشبكات المشتركة. تحدي bot عند الحاجة لا بديلًا عن authorization.
- MFA للإدارة، تهيئة admin أولي آمنة بلا default password منشور. recovery codes محمية، وتغيير البريد/كلمة المرور يتطلب إعادة مصادقة.
- server-side policies على كل عملية وملكية كل طلب. اختبار IDOR، ومنع customer role escalation وmass assignment.
- التحقق من المدخلات، parameterized queries/ORM، escape للمخرجات، وتعقيم المحتوى المنسق بقائمة سماح. ضبط CSP وheaders مع اختبار فعلي لتجنب كسر الواجهة.
- الرفع للإدارة فقط أولًا، allowlist لأنواع وأحجام وأبعاد الصور، فك ترميز وإعادة ترميز raster، أسماء عشوائية، ومنع SVG/HTML والملفات التنفيذية غير المعقمة. ملفات حساسة private بروابط مؤقتة مع صلاحية عند الحاجة.
- الأسرار خارج Git والواجهة وملفات Vite العامة؛ DB private مع حساب خدمة محدود. تشفير اتصالات قواعد البيانات حيث تدعمه الاستضافة.
- production debug مغلق، رسائل خطأ عامة، وسجلات بلا كلمات مرور أو cookies أو كامل طلبات العملاء. تنقيح البيانات في مراقبة الأخطاء.
- فحص تبعيات وأسرار في CI، مراجعة صلاحيات Git والنشر، تحديثات دورية، وسجل تدقيق لأفعال الإدارة.
- نسخة احتياطية مشفرة مستقلة واختبار restore، وخطة للاستجابة للتسريب أو تعطل الخدمة.

لا يوجد أمان مطلق أو وعد بعدم الاختراق؛ نربط الحماية بمعايير قبول واختبارات ومراقبة وتشغيل مستمر.

## 11. الأداء والاعتمادية

- تحميل صور مضبوطة الحجم مع lazy loading ونسخ responsive، CDN للأصول المحلية والخطوط، وbundle splitting إذا أظهر القياس حاجة.
- كاش للمحتوى العام فقط، invalidation بعد النشر، مع منع cache للجلسات والإدارة والملفات الخاصة.
- فهارس وpagination وقياس SQL، منع N+1، سقف اتصالات DB وضبط timeouts، وعدم تشغيل أعمال ثقيلة في request المستخدم.
- Queue للإشعارات والمعالجة مع retry/backoff وfailed-jobs ومراقبة تأخر الصف. تعطل البريد لا يوقف التصفح أو يضيع الطلبات.
- health/readiness checks تميّز تشغيل التطبيق من جاهزية DB، uptime monitoring وإنذارات أخطاء وذاكرة ومعالج وstorage وqueue.
- لا نساوي عدد زيارات شهري بعدد مستخدمين متزامنين. نختبر معدلات الطلبات وسيناريوهات واقعية على بنية قريبة من الإنتاج.

معيار قياس أولي مقترح: 100 جلسة متزامنة تتصفح وتبحث بوقت تفكير واقعي مدة15دقيقة، ثم spike إلى300 لمدةدقيقتين، على staging وببيانات اصطناعية وبريد معطل/وهمي. هذه أهداف اختبار وليست قدرة مثبتة أو توقع جمهور. نقيس public reads وauthenticated writes بصورة مستقلة؛ هدف مبدئي p95 API reads أقل من500ms من منطقة الاختبار، و5xx أقل من1%، وعدم ضياع/تكرار طلبات. نختبر rate limiting منفصلًا ولا نعتبر429المقصودة نجاحًا للطلبات الطبيعية. الحدود تُراجع حسب الاستضافة والميزانية ونتائج القياس من فلسطين وألمانيا.

## 12. الخصوصية والتشغيل التجاري

نجمع أقل بيانات لازمة ونحدد من يراها وفترة الاحتفاظ والحذف والتصدير. نحتاج هوية الجهة المسؤولة ووسيلة طلب الخصوصية وسياسة منشورة قبل استقبال حسابات حقيقية. لا نضيف analytics/marketing cookies افتراضيًا. استهداف مستخدمين بألمانيا وتخزين حساباتهم يستدعي تقييم متطلبات الخصوصية والعقود ونقل البيانات مع المختص؛ لا نعد هذه الوثيقة إقرار امتثال GDPR أو نصًا قانونيًا. لا نجمع معلومات دفع أو هويات شخصية لهذا التدفق.

## 14. الاختبارات اللازمة قبل الإطلاق

- Integration: ضيف/عميل/محرر/مبيعات/مدير، وعميل A يحاول قراءة أو تعديل طلب B، ومحاولات role escalation.
- Auth: CSRF، session invalidation، reset token انتهاء/استخدام واحد، MFA، email verification، rate limits، وعدم تسريب وجود حساب في الأخطاء.
- Content: draft لا يظهر، حفظ وترجمة ونشر وcache invalidation، تعارض slug/legacy ID، وتحقق الملفات.
- Inquiry: transaction rollback، idempotency، قيمة/وحدة كمية غير صالحة، variant لا ينتمي للمنتج، archived product، snapshots بعد تعديل الكتالوج، تعطل البريد وإعادة المحاولة.
- React Query: مفاتيح تشمل اللغة والفلتر والصفحة والصلاحية والهوية عند الحاجة؛ loading/error/empty/refetch؛ cache shape وsetQueryData/invalidation الموجّه بعد CRUD؛ pagination totals؛ إلغاء القراءات المتأخرة عند logout وتبديل الحساب؛ اختبار فشل mutation وعدم تكرار طلب توريد عند retry؛ بقاء التصميم والـFlow.
- UI/E2E: العربية/الإنجليزية، RTL/LTR، deep links، إعادة تحميل، عودة المتصفح، keyboard/dialogs، الاستمرار بعد login، توجيه لوحة الإدارة.
- Performance: k6 وسيناريو cold/warm cache، steady/spike، CPU/RAM/DB/queue وملف نتائج، لا production load test بلا إعداد.
- Operations: DB restore على بيئة منفصلة، health/readiness، انقطاع خدمة البريد، فشل deployment وrollback؛ لا نقول الاختبار passed قبل تنفيذه.

## 15. أسئلة غير محسومة وخطوة البدء

- تفضيل Laravel أو Node.js/TypeScript.
- تأكيد أن الطلب RFQ وليس شراءً ملزمًا؛ الخطة تعتمد RFQ مؤقتًا.
- استلام أحدث كود Make؛ النسخة المحلية الحالية غير كافية للربط النهائي.
- ميزانية التشغيل، جهة ملكية الدومين والبريد، ومن سيملك حسابات الاستضافة.
- اعتماد منتجات2026وتعارضات الأحجام، ولغات الإطلاق الفعلية وأهلية استقبال الطلبات التجارية.

البدء العملي: تثبيت أحدث نسخة frontend في Git، تصميم migrations والعقد الأول لمنتج/عبوة، ثم ربطه من PostgreSQL إلى API إلى Service ثم Query Hook ثم بطاقة المنتج الحالية، وفق القسم3A، مع التحقق من الرد الحقيقي قبل كتابة mapping. لا تُشترى استضافة أو يُنشر شيء بهذه الخطة.
